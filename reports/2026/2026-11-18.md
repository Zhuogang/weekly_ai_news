- **Self-improvement needs an address.** Did the improvement land in model weights, a memory store, generated code, or the surrounding harness? This issue has unusually useful examples of the distinction.

## 1. GPT-6.2 Astra and Sol: a consequential launch, with an instructive disclosure boundary

*Released November 17*

OpenAI released both models through ChatGPT Work, Codex and the API, emphasizing professional outputs, coding, computer use and efficiency. Standard API prices per million tokens are **Astra: $8 input / $0.40 cached / $40 output; Sol: $2 / $0.10 / $10**.

The more interesting research news is the system card. OpenAI says Astra reaches its **High threshold for AI Self-Improvement**, assessed through research-engineering evaluations. It also discloses internal use for generating training data, evaluating and monitoring models, and assisting research.

That establishes a public claim about AI-assisted R&D. It does **not** disclose a reproducible sequence of autonomous successor models with compounding gains. The card also reports that Epoch AI observed no meaningful improvement over the prior Astra on its tested open-ended research tasks. Capability gains depend on what you measure.

**My take:** compare accepted research outputs per dollar and researcher-hour. A faster implementation assistant and a better experiment designer are separate capabilities.

For your team, try a fixed, previously solved investigation: diagnose a recognition regression, propose an ablation, implement it, and explain the result. Score hypothesis quality separately from patch correctness. Hidden training mixtures, compute allocation and the detailed causes of the release’s improvements remain undisclosed.

Sources: [release](https://openai.com/index/introducing-gpt-6-2-astra-sol/) · [system card, including AI R&D evaluations and external assessments](https://deploymentsafety.openai.com/gpt-6-2-astra-sol/additional-informational-assessments-2)

## Pushing the frontier: better models, better use.

### 2. CompoundingKernel: the accumulated artifact is code

*Submitted November 14; late discovery*

Amazon’s system keeps an external archive of correct GPU kernels and their lineage. An LLM controller selects parents or new designs; child agents edit, compile and measure candidates. External checks determine correctness. People still choose submissions and allocate compute using standings.

The authors report **4.40× geometric-mean speedup over the reference baseline** on 209 public SOL-ExecBench problems. At equal wall time, their controller beats a coded UCB-style search on **35 of 38 problems**, producing 2.4× as many correct attempts; per-attempt selection quality was similar.

That last detail matters: the advantage is partly productive experiment throughput, rather than magical proposal quality.

**What improves:** kernels, external memory and occasionally the harness—not model weights. Over a thousand agent sessions ran concurrently. Most gains arrived early, with diminishing returns. A total dollar cost was not verified.

This is measured iterative code optimization, including agent assistance on its infrastructure; it does not establish autonomous recursive improvement of general intelligence. Benchmark-specific tests and B200 timings constrain the result.

The paper advertises code and kernels, but its linked explorer was inaccessible during verification.

**Try the principle:** retain correct-but-slow implementations and lineage. They may become useful stepping stones; a winner-only archive erases that option.

Sources: [paper and controller comparison](https://arxiv.org/html/2611.19230v1) · [author-linked artifact explorer; access unverified](https://huggingface.co/spaces/QianQu/CompoundingKernel-Explorer)

### 3. Context versus weights: memory wins first; RL adds something different

*Submitted November 15*

An Apple/UC San Diego study compares retained experience, GRPO and self-distillation on matched task streams. Crucially, it scores each arriving task **before adapting to that task**.

With Qwen3.5-9B across 109 tasks and four environments, the best standalone context policy lifts mean success from **28.8% to 49.4%**; adding GRPO reaches **51.6%**. Context reduces repeated lookups but can encourage skipped inspection and verification. GRPO helps restore those behaviors.

**The loop:** attempt tasks → receive environment feedback → retain episodes and/or update a persistent LoRA adapter → evaluate later tasks. Context changes the input; RL changes weights. Humans supply environments, rewards and adaptation rules.

The compute caveat is substantial: GRPO receives 32 attempts per task and eight optimizer steps; self-distillation gets 48 attempts and three steps. These are comparisons of procedures, not equal-compute objectives.

This supports online specialization, not indefinite recursive acceleration. One model and short, related task streams limit generalization. I did not verify a public code or checkpoint release.

**For your workflows:** measure whether memory improves reusable environment knowledge while making the agent overconfident about the current scan. Keep “knows the schema” separate from “checked this record.”

Source: [paper, protocol and complete adaptation settings](https://arxiv.org/html/2611.19700v1)

**The practical distinction across these reads:** persistence alone is insufficient evidence of recursion. A code archive can improve while the proposer stays fixed. A trained adapter can improve while its learning algorithm stays fixed. Stronger RSI evidence would show that the system improves its own improvement process, with fresh evaluations across successive cycles and compute accounted for.

## 4. MMFlash: speed up the tokens that actually need the image

*Submitted November 13; late discovery through HF’s November 16 feed*

Speculative decoding lets a cheap drafter propose a token block that the target verifies. The snag for VLMs: tokens grounded in the image are harder to draft.

MMFlash measures visual dependence using the divergence between target predictions with and without the image. It upweights visually dependent tokens the drafter predicts poorly, and uses sparse draft attention for long videos.

The paper reports average greedy decoding speedups around **3.00–3.05×**, **6.7–10.9% above DFlash**, across its two target models. Main measurements use one H200 and concurrency one. Higher-concurrency results show smaller gains.

**Why I like it:** the training objective targets the source of rejected blocks, rather than treating every token as equally useful supervision.

The public repository includes training/evaluation code and lists released target-specific draft checkpoints. The drafter consumes target hidden states, avoiding another visual encoding pass. These drafts are companions to specific target models, not standalone replacements.

“Lossless” refers to preserving target decoding behavior, not correcting the target’s visual errors. For your product-matching service, measure end-to-end latency: image preprocessing and short structured outputs can leave little decoding time to accelerate.

Sources: [paper](https://arxiv.org/html/2611.18482v1) · [code and serving instructions](https://github.com/fscdc/MMFlash) · [draft checkpoint collection](https://huggingface.co/collections/FSCCS/mmflash)

## 5. PaperCritic: train for defensible criticism, not reviewer vibes

*Submitted November 13; late discovery through HF’s November 17 feed*

A fluent reviewer can generate eight plausible complaints without finding the paper’s real weakness. PaperCritic separates soundness assessment from judgments about novelty or presentation.

Its PaperSound-23K dataset contains about 23,000 human/model review points from 1,000 ICLR submissions. Training rewards an F1-style balance: valid, substantive criticisms for precision, and coverage of high-quality reference points for recall.

The authors report improvements over frontier and alternative reviewer-training baselines on their in-domain evaluation, plus transfer to other review settings. The useful comparison is the reward ablation: preference and similarity rewards versus the explicit precision/recall objective.

**The catch:** soundness still relies on learned judgments, and reference coverage can miss a new, correct objection. Prompts and available input context also differ across some baselines. I did not verify downloadable code, data or weights.

**My take:** borrow its output contract for internal design reviews. Require each criticism to identify a claim, supporting evidence, and why that evidence is insufficient. Then track false accusations as seriously as missed bugs.

This could assist AI R&D, but a better reviewer alone does not demonstrate a closed loop producing better successor models.

Source: [paper, reward design, comparisons and evaluation details](https://arxiv.org/html/2611.17834v1)

## 6. Nemotron for Science: a concrete recipe—and a reward-design warning

*Engineering walkthrough dated November 16*

NVIDIA describes turning experimental records into an RL environment: the model predicts a metabolite from a parent molecule and enzyme, a verifier compares molecular fingerprints using Tanimoto similarity, and GRPO updates LoRA adapters. Optional teacher-generated successful traces provide an SFT warm start.

The post reports a 12% improvement from SFT and a further 17% from RL at a 16,384-token output budget. Read the metric carefully: the accompanying chart measures **mean molecular similarity**, so those figures should not automatically be interpreted as exact-answer accuracy or percentage-point gains.

**The transferable lesson:** existing labeled outcomes can supply training feedback without a separate preference-labeling operation. But a convenient similarity function becomes the optimization target; it may reward structurally similar yet scientifically wrong answers.

The post links public NeMo Gym and NeMo RL tooling. Its example recipe link points to an internal GitLab host, so complete public reproducibility is not established.

For your catalog matcher, the analogy is immediate: rewarding embedding similarity could teach a model to accept the wrong flavor. A verifier needs the decisive identity attributes, not just a smooth proximity score.

Source: [walkthrough, reward and post-training methodology](https://developer.nvidia.com/blog/post-training-nvidia-nemotron-to-increase-accuracy-in-your-scientific-domain/)

## The two deeper reads I’d choose

1. **[Context versus weights](https://arxiv.org/html/2611.19700v1).** Start with the score-before-update protocol and compute-budget table. It gives you a disciplined way to ask whether an agent learned transferable knowledge or merely benefited from another attempt.
2. **[CompoundingKernel](https://arxiv.org/html/2611.19230v1).** Read the archive, controller baseline and measurement-throughput sections together. The interesting system is the experiment loop, not the agent count.

## One concrete experiment: does your agent improve across cases—or memorize the answers?

Use a sandboxed product-catalog investigation task with automatically checkable outcomes. Build three disjoint streams of 20 cases, grouped by retailer or catalog schema, plus a small untouched transfer set.

Compare the same fixed model under three conditions:

- **Stateless:** each case starts fresh.
- **Verified memory:** retain concise schema facts and successful diagnostic procedures.
- **Verified memory plus examples:** also retain solved cases, including their product identities.

Give each condition the same dollar and wall-time budget. Memory consumes tokens, so equal request counts are insufficient. Score each case’s first attempt before adding its outcome to memory. Keep product identities disjoint between learning and transfer cases.

Measure exact root-cause accuracy, confident wrong catalog changes, verification steps performed, latency and cost. At the end, replay the untouched transfer set with and without memory. Manually inspect a sample for catalog mistakes the automatic verifier missed.

**Hypothesis:** procedural memory will help more reliably than copying solved SKU examples, which may encourage stale assumptions or identity leakage. If improvement disappears when memory is removed, you improved the scaffold. That can still be valuable; you have not improved the model’s weights.

If this works, a later adapter-training experiment can test persistent learning. Keep its training cost and a frozen regression suite in the accounting. The question for colleagues: **which knowledge should remain editable memory, and which behavior is stable enough to train into the model?**
